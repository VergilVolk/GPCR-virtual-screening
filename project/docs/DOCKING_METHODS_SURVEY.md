# 结合判定方法学调研：怎么判断一个分子能不能结合进口袋

> 2026-08-22 调研记录。背景：我们之前用 AutoDock Vina 做对接打分，
> 团队提出"太落后了，试试其他 docking 方法"。以下是调研结论与我们的落地方案。

## 一、现状：主流对接/打分工具一览（2024-2026）

| 工具 | 类型 | 硬件要求 | 本机（纯 CPU Windows + py3.13）可行性 |
|------|------|---------|--------------------------------------|
| AutoDock Vina 1.2.x | 经典对接（经验力场） | CPU | ✅ 已用 |
| **GNINA 1.3+** | CNN 增强对接/打分 | Linux + CUDA（官方）；CPU 推理可行但无 Windows 版 | ❌ 无 Windows 二进制 |
| **smina** | Vina 改进（打分/采样/自定义打分） | Linux/macOS（官方无 Windows 版） | ❌ 无 Windows 二进制 |
| **DiffDock** | 生成式盲对接（扩散） | GPU 为主；无 pip 包，需旧版 torch_geometric/e3nn 栈 | ❌ py3.13 装不上 |
| **SurfDock** | 表面感知盲对接 | GPU | ❌ |
| **Uni-Dock** | 超快对接（GPU 优化） | GPU | ❌ |
| **RTMScore** | DL 亲和力打分 | GPU + dgl-cuda 旧栈 | ❌（此前实测环境不可行） |
| **DeepRMSD** | pose 质量评估（预测 RMSD） | CPU 权重存在，但代码为 2022 旧实现 | ⚠️ 不完整（只有 pose 优化脚本） |
| **AutoDock-GPU** | 经典对接加速 | GPU | ❌ |

**结论**：2024-2026 年的先进对接/打分工具（GNINA、DiffDock、SurfDock、Uni-Dock、RTMScore）
几乎全部依赖 Linux + GPU + 特定旧版 Python 栈。**纯 CPU Windows + py3.13 环境下，现成先进工具
不可安装**——这不是我们的能力问题，而是这些工具本身的工程现状。

这个结论对论文有直接价值：赛道三要求"复现前沿算法 pipeline 并找出算法边界"，
**"前沿对接工具在受限计算环境不可复现"本身就是一条可报告的工程边界**，
与我们的"打分失效"实证互为表里（工具难复现 + 复现出来的也不适用于别构 PAM）。

## 二、我们的替代：不依赖力场的"结合判定"

既然先进工具装不上，我们转向**不依赖外部力场/GPU 的结构判定**，与 Vina 正交：

### 1. 变构枢纽药效团（已实现，AUC 0.31→0.74）
机制发现驱动的结构先验：分子必须接触 TYR439 变构枢纽才可能是有效 PAM。
这是"结合判定"的**功能相关**版本——不仅要结合，还要结合在对的位置。

### 2. 形状/接触互补打分（下一步）
用 RDKit 直接计算 docked pose 的：
- 受体-配体接触原子数（埋藏程度）
- 配体原子被受体原子包围的程度（形状互补代理）
这是"能不能结合"的**物理**版本，不经过力场打分，与 Vina 的误差来源正交。

### 3. Vina 能量分项诊断（下一步）
把 Vina 打分拆成 vdW/氢键/静电/扭转项，看哪一项对 PAM 有区分度——
回答"打分失效是哪一项失效"（打分分解诊断）。

### 4. Consensus 集成
Vina + 枢纽药效团 + 形状互补 + QSAR 的共识打分（多数投票/加权）——
单个信号都不可靠，但正交信号交叉验证。

## 三、与"机制创新"的收敛关系

- 打分失效实证（AUC 0.68/0.44）→ 为什么失效（机制：8Å 不接触 + 刚性能量缺失变构项）
- → 怎么修复（不换力场，改用机制驱动的结构先验：枢纽药效团 0.74）
- → 怎么补强（形状互补 + 分项诊断 + consensus，正交信号交叉验证）

这是"从失效到修复"的完整方法学叙事，也是我们收敛的核心：
**在现成工具不可用的约束下，用机制理解替代力场经验，做出有效的结合判定。**
